## (b) The embedded fonts actually render the two new languages

`core/__tests__/pdf-font-coverage.test.ts`, run on its own: **14/14 pass** — four
locale-coverage cases (`zh`, `ja`, `ko`, `ar`), four static-face cases, two
allowance-audit cases and four well-formedness cases. The suite parses the base64
each module ships, walks its `cmap` computing glyph ids (so a range mapped to
`.notdef` is never counted as covered), and fails if a character the locale
displays has no glyph, if any embedded face is still variable, or if a face named
bold reports a weight under 600.

Font modules verified byte-identical to the pin by SHA-1 (`notoJP.ts`,
`notoKR.ts`, `notoSC.ts`, `notoArabic.ts`, `roboto.ts`, `fonts/loader.ts`). Sizes
on disk: 290,858 / 3,239,261 / 302,651 / 289,605 / 75,135 bytes.

### Deviation (7): the one `KNOWN_GAPS` entry this port adds

`zh: [0x5e93]` — 库 ("library"). It reaches the Chinese locale only through this
port's own `credits.originalProjectDesc` ("the React library this Angular port is
based on"), a string upstream does not have, and `notoSC.ts` is subset upstream
from **upstream's** locale, so it carries no glyph for it. The string is
on-screen only: no PDF label prints `credits.*`, and the UI draws it with the
browser's own fonts, not the embedded subset. The alternative — regenerating the
subset from this port's locale — would ship font bytes that differ from the
pinned blob, which is precisely what the core-verbatim rule exists to prevent.

The entry cannot quietly outlive its reason: the test's own allowance audit
asserts each allowed codepoint is genuinely **absent from the font** and
genuinely **used by the locale**, so a future upstream regeneration that happens
to cover 库 turns the suite red until the entry is deleted.

## (f) The code-split guard that was missing

Upstream's guard proving every non-English language is reached through a literal
dynamic import lives in `i18n-lazy-load.test.tsx`, which this port must exclude
from `test:corpus` (it mixes static analysis with React render assertions). The
Angular replacement, `lib/lazy-loading.guard.spec.ts`, had ported only that
file's two static-import scans — so **no executed test in this repo had ever
checked that claim, for any language.** It is now ported, derived from
`LANGUAGES` (which is what makes it cover a language added later) plus the static
`import en` assertion, and it runs under `test:ng`. `vitest.config.ts`'s
`covered-by:` annotation for the excluded file was corrected to say what is
actually covered.

Counterfactuals run by the task reviewer, each confirming the guard can fail:

| edit | result |
|---|---|
| delete `ko` from the topbar `LANGUAGE_OPTIONS` | red — `topbar: expected [...(12)] to deeply equal [...(13)]` |
| delete `ja` from the Settings `LANGUAGE_OPTIONS` | red — `settings: expected …` |
| `import("./locales/ko")` → `import("./locales/k" + "o")` | red — `ko: expected … to contain 'import("./locales/ko")'` |
| add `import { PDF_FONT_KR } from "../core/fonts/notoKR"` to a shell service | red — "a static import of an embedded font pulls it into the main bundle" |

One real hole was found and closed in the process: the specifier regex inherited
from upstream only matched imports with a `from` clause, so a bare side-effect
import (`import "../core/fonts/notoKR";`) was invisible to all three scans.
Widened — this is the port's own Angular spec, not a core file.
